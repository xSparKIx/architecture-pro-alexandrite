# Архитектурное решение по трейсингу

## Системы, которые необходимо покрыть трейсингом

### Критические системы для трейсинга:

* MES API - ключевой сервис обработки заказов
* Shop API - точка входа для создания заказов
* CRM API - управление клиентами и заказами
* RabbitMQ - асинхронная коммуникация между сервисами
* PostgreSQL - хранение состояния заказов

### Проблемные точки, где заказ может "сломаться" или зависнуть:

* Shop API → RabbitMQ - потеря сообщения при создании заказа
* RabbitMQ → MES API - сообщение не доставлено потребителю
* MES API → PostgreSQL - ошибка сохранения состояния заказа
* Внешние системы → MES API - потеря заказов при ошибках

## Данные для трейсинга

### Базовые данные трейса (OpenTelemetry стандарт):

* traceId - сквозной идентификатор запроса
* spanId - идентификатор операции в сервисе
* parentSpanId - идентификатор родительской операции
* serviceName - название сервиса
* operationName - название операции/метода
* startTime - время начала операции
* endTime - время завершения операции
* duration - длительность выполнения
* status (OK/ERROR) - статус выполнения
* attributes - дополнительные атрибуты

## Бизнес-контекст для заказов:

* orderId - идентификатор заказа
* customerId - идентификатор клиента
* orderStatus - текущий статус заказа
* paymentId - идентификатор платежа
* userId - идентификатор пользователя (для API)

## Технический контекст:

### Для HTTP запросов:

* http.method (GET/POST/PUT/DELETE)
* http.route (/api/orders/{id})
* http.status_code (200, 500, etc.)
* http.url - полный URL
* http.user_agent - клиент приложения

### Для RabbitMQ:

* messaging.destination - название очереди
* messaging.message_id - ID сообщения
* messaging.consumer_id - ID потребителя
* messaging.retry_count - количество попыток

### Для PostgreSQL:

* db.name - название базы данных
* db.operation (SELECT/INSERT/UPDATE/DELETE) - операция
* db.table - название таблицы
* db.rows_affected - количество затронутых строк
* db.query - текст запроса (опционально, для дебага)

## Мотивация

### Проблемы текущей ситуации:

* "Слепые зоны" в обработке заказов - невозможно отследить где именно теряется заказ
* Длительное время диагностики проблем - часы на поиск корневой причины
* Потеря прибыли из-за невыполненных заказов
* Недовольство клиентов отсутствием прозрачности статусов

## Что даст внедрение трейсинга компании:

### Операционные преимущества:

* Сокращение времени диагностики инцидентов с часов до минут
* Возможность проактивного обнаружения проблем
* Прозрачность всего жизненного цикла заказа
* Бизнес-преимущества:
* Снижение потерь от невыполненных заказов
* Улучшение клиентского опыта за счет точного отслеживания статусов
* Обоснование для оптимизации производительности системы

## Технические метрики, на которые повлияет внедрение трейсинга:

### Mean Time To Detection (MTTD) - время обнаружения проблем

* Текущее: 2-4 часа
* Цель: 5-15 минут

### Mean Time To Resolution (MTTR) - время восстановления сервиса

* Текущее: 4-8 часов
* Цель: 30-60 минут

### Service Level Indicators (SLI) для MES API:

* Latency (p95) - снижение на 30%
* Error rate - снижение с 5% до 1%
* Availability - увеличение с 95% до 99.5%

### Эффективность очередей:

* Message processing time - оптимизация на 25%
* DLQ rate - снижение с 10% до 2%

## Бизнес-метрики, на которые повлияет внедрение трейсинга:

### Order Completion Rate (процент завершенных заказов)

* Текущее: 85%
* Цель: 98%

### Order Processing Time (время от создания до завершения)

* Текущее: 4-6 часов
* Цель: 1-2 часа

### Customer Satisfaction Score (CSAT)

* Текущее: 3.2/5
* Цель: 4.5/5

### Lost Order Rate (процент потерянных заказов)

* Текущее: 8-12%
* Цель: <2%

## Компромиссы

### 1. Высокочастотные низкоуровневые операции

Проблема: Инструментирование каждого вызова к БД при высокой нагрузке (тысячи запросов в секунду)

### 2. Синхронные блокирующие операции

Проблема: Добавление трейсинга в критичных по времени операциях может добавить задержку

### 3. Наследуемый код

Проблема: Старый код может потребовать больших доработок и обновления для внедрения, что повлечет за собой дополнительные затраты

### 4. Производительность

Проблема: Трейсинг дает дополнительную нагрузку на системы
Приблизительные затраты:

- CPU: 1-5% на инструментирование
- Память: 50-200MB на сервис
- Сеть: 1-10KB на trace

### 5. Стоимость

Проблема: Трейсинг увеличивает нагрузку на систему и требует дополнительного места для хранения трейсов, что несет за собой дополнительные расходы. Также внедрения трейсинга влечет за собой дополнительные траты на разработку и поддержку.
Приблизительные затраты:

- 1000 заказов/день × 10 spans/заказ = 10,000 spans/день
- Размер: 10,000 × 2KB = 20MB/день
- Итого в год: 7.3GB

## Безопасность

### Аутентификация и авторизация

Доступ к Jaeger UI предоставляется только сотрудникам с валидной корпоративной учётной записью через OAuth2 провайдер (Azure AD / Google Workspace) у которых достаточно прав на просмотр трейсов.

#### Ролевая модель доступа (RBAC):

Роль "Поддержка" — просмотр трейсов для расследования инцидентов, доступ только к операциям поиска и фильтрации
Роль "Разработчик" — доступ к трассировкам в пределах своих сервисов + возможность экспорта трейсов для отладки
Роль "DevOps" — полный доступ к трейсам всех сервисов, настройка семплирования
Роль "Администратор" — управление пользователями, конфигурацией системы, политиками хранения данных

### Ограничение доступа к системе

#### Сетевые ограничения:

* Доступ к Jaeger UI и API разрешён только из внутренней сети компании через VPN
* OpenTelemetry Collector принимает данные только от доверенных источников (white-list IP адресов сервисов)
* Внешний доступ к API трейсинга запрещён, за исключением специально выделенного API Gateway с строгой аутентификацией

#### Многофакторная аутентификация:

* Обязательная MFA для всех пользователей при доступе к системе
* Сессионные ограничения (максимум 8 часов) с автоматическим разлогином

### Шифрование и защита данных

#### Защита передаваемых данных:

* TLS 1.3 для всех коммуникаций между агентами трейсинга и коллектором
* mTLS для взаимной аутентификации компонентов системы
* Шифрование HTTP заголовков с конфиденциальными данными

#### Защита хранимых данных:

* Шифрование "at rest" для базы трейсинга (AES-256)
* Регулярная ротация ключей шифрования (ежеквартально)
* Изолированное хранение чувствительных метаданных

#### Защита PII (персонально идентифицируемая информация) данных:

* Автоматическая санатизация трейсов - удаление персональных данных (email, телефоны, платежная информация)
* Разрешение хранения только технических идентификаторов (Order ID, User ID, Request ID)
* Политика запрета на добавление кастомных тегов с конфиденциальной информацией

### Контроль и аудит

#### Мониторинг доступа:

* Полное логирование всех действий: вход в систему, просмотр трейсов, экспорт данных
* Алёртинг на подозрительную активность: массовый экспорт, доступ вне рабочего времени
* Еженедельные отчеты по активности пользователей

#### Управление доступом:

* Регулярный ревью прав доступа (ежеквартально)
* Автоматическая деактивация учетных записей при увольнении сотрудников
* Своевременное удаление временных доступов для подрядчиков

### Принцип минимальных привилегий

#### Строгое разделение прав:

* Каждый сотрудник получает минимально необходимый для работы уровень доступа
* Запрет на совместное использование учетных записей
* Разделение production и staging окружений

### Временные доступы:

* Для внешних подрядчиков создаются отдельные учетные записи с ограниченным сроком действия
* Автоматическое отзыв доступов по истечении срока проекта
* Ограничение доступа только к конкретным сервисам/проектам

### Дополнительные меры безопасности

#### Резервное копирование и восстановление:

* Шифрованные бэкапы конфигурации безопасности
* Периодические тесты восстановления системы

#### Обновления и исправления:

* Регулярное обновление компонентов системы трейсинга
* Мониторинг уязвимостей в используемых компонентах

#### Обучение сотрудников:

* Обязательный security training для всех пользователей системы
* Регулярные напоминания о политиках работы с трейсами
