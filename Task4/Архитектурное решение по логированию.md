# Архитектурное решение по логированию

## Системы для сбора логов

### MES API

* Событие начала расчетов
* Событие окончание расчетов
* Событие создание заказа
* Сколько заказов в очереди

### Shop API

* Событие создания заказа
* Событие загрузки файла
* Событие изменения статуса заказа
* Событие авторизации пользователя
* Событие неудачной попытки авторизаций

### CRM API

* Событие создания соказа
* Событие изменения статуса заказа
* Событие закрытия заказа

### 3d files storage

* Собственные логи S3 с информацией о запросах к бакетам и объектам

### Базы данных

* В связи с трудностями и потерями заказов можно временно внедрить Write Ahead Log (WAL).
Write Ahead Log (WAL) — механизм в СУБД, который фиксирует изменения данных перед тем, как они окончательно применяются к файлам базы

## Мотивация

Текущая ситуация с разбором инцидентов "со слов клиента" создает серьезные операционные проблемы:

* Время диагностики: 4-8 часов на поиск корневой причины проблем
* Потеря прибыли: Невыполненные заказы из-за невозможности быстрого восстановления
* Недовольство клиентов: Длительное время решения проблем
* Нагрузка на поддержку: Ручной сбор информации от клиентов

### Что даст внедрение централизованного логирования:

* Сокращение MTTR
* Проактивное обнаружение проблем до эскалации от клиентов
* Автоматизация анализа инцидентов
* Прозрачность бизнес-процессов

### Технические и бизнес-метрики

#### Технические метрики:

* MTTR (Mean Time To Resolution)
* MTTD (Mean Time To Detection)
* Покрытие бизнес-критичных операций логами
* Хранение релевантных логов 30+ дней

#### Бизнес-метрики:

* Увеличение удавлетворенности пользователей
* Процент закрытых заказов
* Снижение нагрузки на поддержку

### Приоритизация внедрения

#### Фаза 1 (Критический приоритет):

MES API:
  - Создание/изменение статусов заказов
  - Ошибки расчетов стоимости
  - Очередь обработки заказов

Shop API:  
  - Создание заказов
  - Загрузка 3D файлов
  - Ошибки авторизации

#### Фаза 2 (Высокий приоритет):

CRM API:
  - Изменения в сделках
  - Работа с клиентами
  - Закрытие заказов

Базы данных:
  - Медленные запросы (>100ms)
  - Ошибки транзакций
  - Deadlock'и

#### Фаза 3 (Средний приоритет):

RabbitMQ:
  - Сообщения в DLQ
  - Проблемы доставки

S3 Storage:
  - Доступ к критичным файлам
  - Ошибки операций

### Уровни логирования:

INFO: Успешные бизнес-операции
WARN: Подозрительная активность, повторные попытки
ERROR: Ошибки бизнес-логики, недоступность сервисов
DEBUG: Детальная отладка (только development)

## Предлагаемое решение

Использовать ELK стек.

### Преимущества для нашего кейса:

- Полная интеграция компонентов "из коробки"
- Мощные возможности поиска и анализа
- Активное сообщество и документация
- Подходит для нашего объема данных

### Технологический стек:

* **Filebeat**: Агенты сбора на каждом сервисе
* **Logstash**: Обработка и обогащение логов
* **ElasticSearch**: Хранение и поиск
* **Kibana**: Визуализация и анализ

## Политика безопасности

### Классификация данных

#### Чувствительные данные

* Пароли и токены (НИКОГДА не логировать)
* Персональные данные (маскировать)
* Платежная информация (хэшировать)
* IP адреса (анонимизировать)

#### Маски для чувствительных данных

* Пароль: "***"
* Номера кредитной карты: "****-****-****-####" 
* Почта: "u***@domain.com"
* Номер мобильного телефона: "+7 *** ***-##-##"

### Контроль доступа
  
Разработчики:
* Доступ на чтение всех своих сервисов
  
DevOps:
* Полный доступ к всем сервисам
  
Безопасники:
* Полный доступ на чтение ко всем сервисам
* Доступ к логам аудита

### Политика хранения

#### Стратегия хранения:

Горяче хранилище (Храним логи 7 последних дней):

* Все логи уровня ERROR/WARN
* Бизнес-критичные операции INFO
* Логи аутентификации

Обычные логи (Храним логи за 30 дней):

* Все логи уровня INFO
* Логи доступа
* Метрики производительности

Холодное хранилище (Храним логи за 1 год):

* Логи аудита
* Логи безопасности
* Архив инцидентов

### Система анализа и алертинга

#### Ключевые алерты:

Критические:

* Рост ошибок 5xx
* Падение процент завершения заказа
* Увеличение среднего времени ответа
* Увеличение количества необработанных сообщений в очереди

Бизнесовые:

* Количество заказов меньше нормы
* Появляются неудачные оплаты
* Загрузка файла возвращает ошибку
* Резкое увеличение числа пользователей

Безопасные:

* Большое количество попыток авторизации с одного ip
* Доступ с локаций не свойственных для пользователя
* Анамалии данных
* Попытка неавторизованного доступа к хранилищу S3

### Поиск аномали

* В системе необходимо искать аномалии для предотвращения проблем с порчей данных и различными видами атак (Таких как DDOS-атака)

### Дополнительные меры безопасности

* Доступ только из корпоративной сети
* Логи действий пользователей
* Именные учетные записи
